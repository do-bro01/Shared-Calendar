## 1. 한 줄 요약

**"우리의 추억을 자연어로 검색하는 AI 캘린더"**

일정 · 사진 · 코멘트가 누적된 개인/그룹 데이터를 RAG로 검색하여, 사용자가 자연어 한 문장으로 과거의 순간을 회상·정리할 수 있는 캘린더 챗봇 서비스.

---

## 2. 배경 및 동기

### 2.1 일상에서 마주치는 문제

> "작년 여름에 우리 어디 갔었지?"
> "엄마 생신 때 뭐 했더라?"
> "○○이랑 처음 만난 날 뭐 먹었지?"

이 질문들에 답하려면 현재는 캘린더와 사진 앱, 메시지 기록을 번갈아 뒤져야 한다. 정확한 날짜를 모르면 답을 찾기가 사실상 불가능하다.

### 2.2 기존 도구의 한계

| 도구 | 한계 |
|------|------|
| Google Calendar / Apple Calendar | 단순 키워드 검색만 가능, 의미 기반 검색 불가 |
| Google Photos / iCloud 사진 | 사진은 찾아도 "누구와, 왜" 맥락 없음 |
| 카카오톡 등 메신저 | 일정 정리 도구 아님, 검색 정확도 낮음 |
| Notion / Obsidian | 직접 정리해야 누적됨, 가족·친구와 공유 불편 |

→ **"내 일상 데이터를 자연어로 묻고 즉시 답을 받는" 통합 도구가 없다.**

### 2.3 LLM과 RAG의 가능성

- **LLM**은 자연어 이해·생성 능력이 뛰어나지만 개인 데이터는 학습에 없어 답할 수 없다.
- **RAG (Retrieval-Augmented Generation)** 를 적용하면 사용자 개인의 일정·사진·코멘트를 **검색 가능한 지식 베이스**로 만들 수 있다.
- 결과: 모든 사용자가 **"내 인생을 아는 챗봇"** 을 가질 수 있다.

## 3. 서비스 대상자

### 3.1 핵심 타겟

**연인 · 가족 · 친구로 구성된 3~6명의 친밀한 그룹.**

- 데이터를 함께 누적하는 데 거부감이 적은 관계
- 추억을 자주 회상하는 정서적 동기 보유
- 모바일 사용에 익숙한 20~40대

### 3.2 페르소나 3종

| 페르소나 | 시나리오 | 핵심 가치 |
|---------|---------|---------|
| **5년차 연인 김민지(28)** | 기념일 아침에 "우리 처음 만난 날 뭐 했었지?" 챗봇에 질문 → 그날의 일정·사진·코멘트가 카드 형태로 표시됨 | 추억 회상 |
| **떨어져 사는 가족 이정훈(35)** | "엄마 작년 생신에 무슨 선물 받으셨더라?" → 누나가 올린 사진·코멘트에서 즉시 답 발견 | 가족 간 기억 공유 |
| **대학 동기 박지원(24)** | "지난 모임 때 OO가 추천한 식당 이름이 뭐였지?" → 모임 일정의 코멘트에서 답변 추출 | 일상 메모 검색 |

### 3.3 서비스가 안 맞는 사용자 (Out of Scope)

- 일정 관리 자체를 잘 안 하는 사람
- 사진/기록을 자주 남기지 않는 사람
- 1회성 사용자 (데이터가 누적되어야 가치가 큼)

## 4. 제안하는 해결책

### 4.1 핵심 기능 (3단계)

1. **수집 (Capture)** — 일정 등록 + 사진 업로드 + 코멘트 작성 (기존 MVP 확장)
2. **저장 (Embed & Store)** — 모든 텍스트와 이미지 설명을 벡터로 변환해 pgvector에 저장
3. **검색 (Retrieve & Generate)** — 자연어 질문 → 유사도 검색 → LLM이 출처 기반으로 답변

### 4.2 사용자 흐름 예시

```
[일상 누적]
4월 15일 일정 추가: "벚꽃 데이트"
   → 4월 16일 사진 3장 업로드 + 코멘트 "윤중로 벚꽃길 끝내줬음"
   → 시스템이 자동으로 임베딩 생성 및 저장

[3개월 후]
사용자: "벚꽃 본 게 언제였지?"
   → RAG 검색: 4월 15일 일정 + 코멘트 발견
   → 챗봇: "2026년 4월 15일에 윤중로에서 벚꽃 데이트 하셨네요. 사진 3장이 함께 기록되어 있어요. [일정 카드]"
```

### 4.3 차별 기능

| 기능 | 설명 |
|------|------|
| **출처 기반 답변** | 모든 답변에 근거 일정 카드를 함께 제시 (할루시네이션 방지) |
| **그룹 단위 검색** | "우리 가족"이 본 공유 일정·사진까지 함께 검색 |
| **멀티모달 임베딩** | 사진은 Vision API로 캡션 생성 후 임베딩 → 시각 정보도 검색 가능 |
| **챗봇 메모리** | 이전 대화 맥락을 기억해 후속 질문 가능 ("그 다음 주말엔?") |

## 5. RAG의 필요성 — 순수 LLM과 비교

### 5.1 정성적 비교

**시나리오**: 사용자가 "작년 여름 휴가 어디 갔었지?" 라고 질문.

| 항목 | 순수 LLM | RAG 적용 |
|------|---------|---------|
| 데이터 접근 | 사용자 데이터 없음 → 답할 수 없거나 환각 | 검색으로 정확한 날짜/장소 추출 |
| 토큰 비용 | 전체 일정 수백~수천 건을 context에 못 넣음 | 관련 일정 3~5건만 추출하여 비용 절감 |
| 응답 시간 | 입력 토큰이 많으면 느림 | 검색은 100ms 이하, 입력 토큰 적어 빠름 |
| 출처 명시 | 불가 | 일정 ID/날짜 명시 가능 |
| 권한 격리 | 모든 데이터 노출 위험 | RLS와 결합해 그룹별 격리 |

### 5.2 정량 비교 계획 (RAGAS)

15개 이상의 Ground Truth 질문-답변 쌍을 만들어 다음 메트릭을 측정한다.

| 메트릭 | 의미 | 비교 대상 |
|--------|------|---------|
| **Faithfulness** | 답변이 검색된 문서에 충실한가 | 순수 LLM은 측정 불가 (출처 없음) → RAG의 우위 |
| **Answer Relevancy** | 답변이 질문에 얼마나 적절한가 | 두 방식 모두 측정 |
| **Context Precision** | 검색된 문서 중 답변에 실제로 쓰인 비율 | RAG만 측정 |
| **Context Recall** | 정답에 필요한 정보가 검색에 포함되었는가 | RAG만 측정 |

**비교군 설계**
1. Baseline: 순수 LLM (시스템 프롬프트만, 전체 일정을 텍스트로 dump)
2. RAG (Basic): 단순 벡터 검색 + LLM
3. RAG (Advanced): Hybrid Search (BM25 + Vector) + Re-ranking + LLM

## 6. 차별성 (다른 RAG 프로젝트 대비)

| 차별 포인트 | 설명 |
|----------|------|
| **개인 RAG 영역** | 기존 RAG 사례 대부분이 공개 문서/사내 문서 대상. 본 프로젝트는 **개인 일상 데이터 RAG**라는 비교적 새로운 영역에 도전 |
| **공유 그룹 RAG** | 권한 격리(RLS) + 벡터 검색을 결합. "우리 가족만 검색 가능한 RAG"라는 차별 |
| **멀티모달** | 텍스트 + 이미지 캡션 통합 임베딩 |
| **모바일 친화 UI** | 다수 RAG 데모가 Streamlit 단순 UI에 그치는 반면, React Native 앱에 자연스럽게 통합 |
| **작은 데이터 RAG의 실효성 검증** | "데이터 수십~수백 건 규모에서 RAG가 정말 의미가 있는가?" 정량 평가 |

## 7. 기대 효과

### 7.1 사용자 가치
- 자연어 한 줄로 인생의 기억을 정리하고 재발견
- 가족·연인과의 추억을 능동적으로 회상하는 도구
- 디지털 일기 + 캘린더 + 검색의 통합

### 7.2 기술적 기여
- **개인 데이터 RAG**의 권한 격리 패턴 (pgvector + RLS) 제시
- **작은 데이터셋(< 1000건)** 에서의 RAG 성능 분석
- **멀티모달 임베딩의 일상 적용** 사례

### 7.3 사회적 의미
- 디지털 기록 시대의 추억 보존 도구
- 가족 간 소통 활성화

## 8. 미해결 의문점 (Open Questions)

| 의문 | 대응안 |
|------|--------|
| 신규 사용자는 데이터가 없어 RAG가 무의미 | **합성 데이터** (가상 사용자 "○○이가 2년간 쌓은 500개 일정 + 사진") 생성하여 데모 |
| 주관적 질문 ("우리 관계 어땠어?") 의 평가 | 사실 기반 질문 위주로 Ground Truth 구성, 주관 질문은 보조 |
| 임베딩 비용 | 사용자당 데이터 양이 적어 비용 미미 (예상 < $0.01/사용자/월) |
| 한국어 임베딩 품질 | OpenAI text-embedding-3-small 또는 한국어 특화 임베딩 모델(BGE-Korean 등) 비교 검토 |
| 사진 캡션 생성 비용 | 업로드 시점에 1회만 생성 후 저장 (Vision API 호출 누적 방지) |
