## 0. 들어가며 — "포기했던 프로젝트를 다시 꺼내든 이유"

이 프로젝트는 **사실 새로 시작한 게 아니다.** 예전에 한 번 만들다가 중단했던 개인 프로젝트였다. 그때 멈춘 이유는 한 마디로 **"서비스를 만든다"는 게 뭔지 몰라서**였다.

- **배포(deployment) 단계에 대한 지식이 전혀 없었다.** "내 컴퓨터에서 돌아가는 앱"을 어떻게 다른 사람이 접속할 수 있는 형태로 올리는지, 환경 변수가 무엇이고 빌드 산출물이 무엇인지 개념 자체가 없었다.
- **SQL과 DB 개념이 없었다.** 데이터를 어디에 저장하고 어떻게 권한을 걸고 어떻게 관계를 표현하는지가 막연했다. 그래서 그냥 메모리/로컬 스토리지에 잠깐 쌓아두는 수준의 시도만 가능했다.
- **"서비스화"라는 감각이 없었다.** 인증, 사용자 격리, 권한, 동기화, 배포 — 이 모든 게 하나의 흐름으로 묶여서 비로소 "서비스"가 된다는 걸 몰랐다. 그래서 결과물은 **로컬에서 혼자 돌려보는 데모** 수준에서 멈췄다.

이번에 AI와 협업하면서, 이 세 가지가 동시에 풀렸다. RLS와 OAuth 같은 구체적인 벽도 있었지만, 더 큰 변화는 **"기능 → 권한 → 동기화 → 배포"**라는 서비스의 전체 그림을 처음으로 끝까지 따라가본 경험이다.

또 하나 명확히 한 점: **최종 사용 환경은 모바일이다.** 캘린더 앱은 손에 들고 즉시 약속을 확인/등록하는 도구라 모바일에서 잘 동작하는 게 핵심이다. 그래서 화면 크기, 터치 영역, 스크롤 동작 등을 처음부터 모바일 기준으로 설계하고, 웹은 같은 코드베이스(`react-native-web`)로 부수적으로 같이 돌아가게 만들었다.

그래서 이 회고의 핵심 질문은 두 가지다:

1. **AI 협업이 정확히 어떤 벽을 깨줬는가?**
2. **그 결과 만든 코드를 나는 진짜로 이해하고 있는가?** — 단순히 AI가 짜준 걸 붙여넣은 게 아니라, 내가 설명할 수 있는가?

## 1. 기능적 회고 — 기획대로 구현되었는가

### 기획 vs 구현 매핑

| 핵심 기능 | 기획 | 구현 결과 | 비고 |
|----------|------|----------|------|
| Google OAuth 로그인 | ✅ | ✅ 웹/iOS/Android 모두 동작 | 모바일은 Expo Go에서만 검증 |
| 개인 일정 CRUD | ✅ | ✅ | 단일/기간 일정 모두 지원 |
| 공유 달력방 CRUD | ✅ | ✅ | |
| SC ID 친구 추가 | ✅ | ✅ | 6자리 영숫자 |
| 친구 삭제 | ✅ | ✅ | 13:52 커밋에서 마지막 추가 |
| 개인↔공유 일정 연결 | ✅ | ✅ | 양방향 cascade 삭제까지 |
| 실시간 동기화 | ✅ | ✅ | 4개 테이블 모두 Realtime |
| 다크/라이트 테마 | ✅ | ✅ | AsyncStorage 영속 |
| 푸시 알림 | ❌ (제외) | ❌ | v1.0 범위 외 |
| 반복 일정 | ❌ (제외) | ❌ | v1.0 범위 외 |

**결론**: v1.0 스펙 기준으로 **기획한 기능은 전부 구현됨**. 과거에 포기했을 때는 로그인조차 동작하지 않았는데, 이번엔 끝까지 갔다.

### 도중에 바뀐 결정

1. **"방 삭제는 생성자만"에서 "혼자 남았을 때만 삭제"로 변경**
   - 이유: 생성자가 먼저 나가버리면 방이 영원히 안 지워지는 문제 발견.
   - 영향: 더 직관적이고 안전한 정책. RLS도 단순해짐.

2. **친구 모델: "요청-수락"을 검토했지만 "즉시 등록"으로 결정**
   - 이유: MVP 단순화 + 친한 관계라는 사용자 가정상 즉시 등록이 더 자연스러움.
   - 트레이드오프: 모르는 사람이 SC ID를 알아내면 일방적 등록 가능. 단, SC ID는 6자리(32^6 ≈ 10억 경우의 수) + 친구가 되어도 일정이 자동 공유되진 않음(별도 방 초대 필요)이라 위험 낮음.

3. **일정 연결의 cascade 방향 — 삭제만, 수정은 아님**
   - 이유: 양쪽 모두에서 같은 일정을 수정하면 충돌 처리가 복잡. MVP에서는 삭제 cascade만 충분.

## 2. 기술적 회고 — 코드를 이해하고 설명할 수 있는가

이 섹션은 자기 검증용이다. 내가 작성한(또는 AI와 같이 작성한) 코드를 **누가 물어봐도 설명할 수 있는지** 짚어본다.

### 2.1 왜 `auth.users`(Supabase)와 `users`(앱) 두 개 테이블인가?

`auth.users`는 Supabase Auth가 관리하는 테이블이고, OAuth 정보(이메일, 프로바이더 등)가 들어간다. 앱 도메인 데이터(SC ID, display_name 등)는 거기에 직접 추가할 수 없으므로 별도의 `public.users` 테이블에 1:1로 연결한다. `auth_id` 컬럼이 외래키.

이 분리 덕분에 Supabase의 인증 인프라(세션 관리, 토큰 갱신 등)를 그대로 쓰면서 앱 도메인 모델은 자유롭게 확장할 수 있다.

### 2.2 친구 관계의 ID는 왜 `{sorted_uid1}_{sorted_uid2}`인가?

친구 관계는 양방향이지만 **레코드는 1개만 있어야 한다**(A↔B와 B↔A를 둘 다 저장하면 동기화 부담이 큼). 두 사용자 ID를 정렬해서 결합하면 어느 쪽에서 추가했든 같은 ID가 나온다.

```js
const [user1, user2] = [user.id, targetUserId].sort();
const friendshipId = `${user1}_${user2}`;
```

스키마 레벨에서도 `check (user1 < user2)` 제약으로 강제한다 ([shared_calendar_initial_schema.sql:34](../supabase/migrations/shared_calendar_initial_schema.sql#L34)).

### 2.3 RLS WITH CHECK는 왜 명시해야 했나?

`for update using (auth.uid() = any(members))`만 쓰면, USING이 **수정 후 새 행**에도 적용된다. 즉 자기 자신을 멤버에서 빼면 새 행에서 자기가 없어지므로 USING 실패.

해결책 두 가지:
- (A) `with check (true)`로 새 행 조건 완화 → 다른 멤버를 강제로 빼는 우회 가능 ⚠️
- (B) `SECURITY DEFINER` RPC로 RLS 우회 + 함수 내부에서 직접 권한 검사 ✅

이 프로젝트는 B를 선택했다 ([leave_group_calendar_rpc.sql](../supabase/migrations/leave_group_calendar_rpc.sql)). 함수 안에서 `auth.uid() = any(members)`를 명시적으로 체크하므로 보안 우회가 불가능.

> AI가 처음엔 (A)를 추천했는데, 보안 영향을 다시 물어보고 (B)로 바꿨다. 이게 이 프로젝트에서 **가장 중요한 학습**이었다 — AI는 "동작하는 답"을 빠르게 주지만 "안전한 답"인지는 사람이 검증해야 한다.

### 2.4 cascade 삭제의 `skipCascade` 패턴

```js
async deletePersonalEvent(eventId, skipCascade = false) {
  if (!skipCascade) {
    // 연결된 그룹 일정들도 삭제 — 이때 skipCascade=true로 호출
    for (const id of linkedGroupEventIds) {
      await GroupEventService.deleteGroupEvent(id, true);
    }
  }
  // 자기 자신 삭제
  await supabase.from(...).delete().eq('id', eventId);
}
```

서로가 서로를 호출하는 양방향 cascade에서 무한 루프를 막기 위한 가드. 첫 호출은 cascade 로직을 타고, 그 안에서 부르는 두 번째 호출은 자기만 지운다.

### 2.5 `members UUID[]` 비정규화 선택

정석은 `group_members(group_id, user_id)` 조인 테이블이지만, **친한 관계 그룹은 보통 2~6명**이라 배열이 더 효율적이다.

- 가입한 방 목록 조회: `where members @> array[uid]` (GIN 인덱스 사용)
- 멤버 추가/제거: 배열 함수(`array_append`, `array_remove`)
- 트랜잭션 1번이면 끝.

조인 테이블이었다면 두 번 쿼리하거나 JOIN이 필요했을 것이다.

### 2.6 OAuth 웹/모바일 분기

웹은 브라우저가 redirect를 처리하지만, 모바일(Expo Go)은 직접 인앱 브라우저를 띄우고 콜백 URL의 `code` 파라미터를 파싱해서 `exchangeCodeForSession`으로 세션을 발급받아야 한다.

[AuthService.js:9-51](../src/services/AuthService.js#L9-L51)에서 `Platform.OS === 'web'`로 분기. 이 부분이 **과거 시도에서 가장 막혔던 지점**이었다.

## 3. 사용성 회고 — 사용자가 쓸 만한가

### 3.1 직접 써본 결과 (셀프 테스트)

두 개의 다른 Google 계정으로 로그인해서 시나리오를 돌렸다.

**잘 동작하는 점**
- ✅ 로그인 → SC ID 발급 → 친구 추가 → 방 만들기 → 일정 추가 → 상대방 화면에 반영, 체감 1초 미만.
- ✅ 다크 모드 전환이 즉시 적용되고 재시작 후에도 유지.
- ✅ 일정 연결 옵션을 켜면 두 곳에 같은 일정이 동시에 생기고 한쪽 삭제가 반대쪽까지 정리됨.

**아쉬운 점 (실제 사용자라면 불편할 부분)**
- ⚠️ **시간(시:분) 단위가 없다.** "오후 7시 데이트"가 안 됨. 날짜만으로는 약속 잡기에 부족할 수 있다 → v1.1 우선순위.
- ⚠️ **알림이 없다.** 약속 1시간 전 알림 같은 게 없으니 "잊지 않게" 라는 핵심 가치를 절반만 달성.
- ⚠️ **친구 추가가 즉시 등록 모델이라 모르는 사람이 SC ID 알아내면 등록됨.** 다만 친구가 되어도 일정은 자동 공유되지 않으므로 위험은 낮음.
- ⚠️ **달력방 멤버 표시 UI가 약하다.** 현재는 멤버 수만 보임. 누가 어떤 일정을 만들었는지 시각적으로 더 명확해야 함 (group_events.user_id를 활용하는 작업 필요).

### 3.2 타겟 사용자에게 정말 가치가 있는가?

처음 정의한 타겟은 **"팀플 그룹"**과 **"연인"**이다.

- **연인 시나리오**: ✅ 확실히 유용함. "그때 우리 며칠에 보기로 했지?"를 한 번에 해결. 연결 일정 기능이 데이트와 본인 시험 일정을 같이 보는 데 유용.
- **팀플 시나리오**: ⚠️ 부분적으로 유용. 시간 단위가 없어서 회의 시간 잡기엔 부족. 다만 "회의 후보일 좁히기" 정도까진 충분.

**결론**: 연인 시나리오는 v1.0으로 충분, 팀플 시나리오는 시간 단위가 추가되어야 완성도 있음.

## 4. 개발 과정 자체에 대한 회고

### 4.1 가장 인상적이었던 순간

**"몇 일 헤매던 RLS 문제가 30분 만에 풀린 순간"**. 과거에 포기했던 바로 그 지점에서 AI에게 정확한 질문을 던졌더니 USING과 WITH CHECK의 동작 차이를 명확히 설명해줬다. 그 순간 "이번엔 끝까지 갈 수 있겠구나" 확신이 생겼다.

### 4.2 AI 협업의 좋은 점과 한계

**좋은 점**
- 학습곡선이 가파른 영역(RLS, OAuth 웹/모바일 분기)을 빠르게 넘어감.
- 데이터 모델링 트레이드오프(정규화 vs 비정규화)를 즉시 비교할 수 있음.
- 보일러플레이트 작성 시간이 거의 0.

**한계**
- AI가 처음 주는 답이 항상 최선은 아님(보안 사례). **2~3번 다시 물어봐야** 더 좋은 답이 나옴.
- AI는 "이 프로젝트의 맥락"을 매번 재설명하지 않으면 일관성이 흐트러짐(인자 형식 통일 안 됨 등).
- 검증은 결국 사람이 직접 해야 함. Supabase 대시보드에서 SQL을 돌려보고, 두 디바이스에서 실시간 동기화를 눈으로 확인하는 일은 AI가 대신해줄 수 없음.

### 4.3 "AI가 만든 걸 그냥 붙여넣었다"고 할 수 있는가?

아니. 검증/리팩터링/결정은 모두 사람이 했다.

- RLS 정책 변경 → Supabase 대시보드에서 직접 SQL 실행 후 확인.
- "혼자 남았을 때만 삭제" 정책 변경은 **사용 시나리오를 직접 따라가다가 발견한 버그**가 발단.
- 친구 즉시 등록 vs 요청-수락 결정도 사람의 판단.
- 인자 컨벤션(객체 인자 통일) 같은 코드 품질 결정도 사람.

코드 한 줄씩 짚어가며 "왜 이렇게 짰는지" 설명할 수 있고, 그게 위 2번(기술적 회고)에 나온 6개 항목이다.

## 5. 다음 버전(v1.1)을 위한 메모

우선순위 순:
1. **시간(시:분) 단위 일정** — 팀플 시나리오 완성도.
2. **푸시 알림** — Expo Notifications + Supabase Edge Function.
3. **친구 요청-수락 모델** — 무방비 등록 차단.
4. **일정 작성자 표시 UI** — 그룹 일정에 누가 만들었는지 시각화.
5. **반복 일정** — RRULE 지원.
6. **모바일 정식 배포** — App Store / Play Store.
7. **SC ID 재발급** — 노출됐을 때 갱신 가능하도록.

## 6. 마치며

처음에 적은 두 질문에 답해보자면:

> **AI 협업이 정확히 어떤 벽을 깨줬는가?**

도메인 학습곡선이 가파른 부분(RLS, Supabase OAuth, Postgres 함수)에서 **"옳은 질문 형태"**를 알려줬다. 혼자였다면 공식 문서 → 블로그 → Stack Overflow를 며칠 떠돌았을 부분이 한 번의 정확한 답변으로 풀렸다.

> **그 결과 만든 코드를 나는 진짜로 이해하고 있는가?**

위 2.1~2.6에서 코드 한 줄 한 줄의 이유를 설명할 수 있다. 단, **이해하지 못하는 부분이 0**이라고 말하진 못한다 — `react-native-reanimated`의 worklet 동작이나 expo-router의 내부 동작은 여전히 블랙박스에 가깝다. 다만 **이 프로젝트의 핵심 도메인 로직**(인증, RLS, 일정 연결, Realtime)은 직접 설명 가능하다.

가장 큰 수확은 **"포기했던 걸 다시 꺼내서 끝낼 수 있다"**는 경험 자체였다. 다음에 또 막히는 프로젝트가 생겨도, 이번처럼 다시 도전할 수 있을 것 같다.
